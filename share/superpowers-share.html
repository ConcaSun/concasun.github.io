01第一部分：Superpowers 是什么

Superpowers 官方一句话把它定义为：

Superpowers is a complete software development methodology for your coding agents, built on top of a set of composable skills and some initial instructions that make sure your agent uses them.

翻译过来是：一套面向你的编码 Agent 的、完整的软件开发方法论，构建在「一组可组合的 skill」与「一些确保你的 Agent 真的会用它们的开场指令」之上。

这个仓库存放在 GitHub 的 obra/superpowers，由 Jesse Vincent 及其所在的 Prime Radiant 团队维护，是 AI 编程社区里高关注度快速走红的一个开源项目（准确的 star 数以上方引区块↑与发布时 GitHub 页面为准）。文中谈到的目录、标签与写法均来自对主干源码的第一手阅读。

嵌套的根目录：它不是代码工程，而是一个「插件仓库」

在 git clone 之后，仓库顶层是这样（skills/ 是所有方法论的载体）：

skills/            # 14 个 skill，每个一个子目录
hooks/             # SessionStart 等由宿主 harness 在会话级触发的脚本
scripts/           # 打包、发布、同步用辅助脚本
assets/            # 图片等
tests/             # shell-lint、插件同步、harness 集成等测试
docs/              # 面向各 harness 的安装/移植说明
*.plugin           # 各家 harness 的插件清单入口
CLAUDE.md / AGENTS.md / GEMINI.md   # 同名 contributor 指引，分别给不同宿主读取

值得注意：它不是一个普通 Python/npm 应用仓库，而是一个「skills + 插件清单 + session-start hook」的组合体，通过适配不同 harness 的插件入口（.claude-plugin、.codex-plugin、.opencode/plugins、.pi/extensions……）被装入各家宿主。

内置的 14 个 skill 家族

仓库实测有 14 个 skill（skills/ 下各一个子目录、每份都是独立 SKILL.md）：

Skill一句话职责归属
using-superpowers会话启动引导，教 agent「先查 skill 再用」，强制技能纪律元技能 / 启动
brainstorming动手写码前先澄清意图，小需求给出短大纲、大需求走完整设计流程流程
test-driven-developmentRED–GREEN–REFACTOR 真·红绿测试驱动测试
systematic-debugging不瞎猜，按 root-cause 才修复（4 阶段根因）调试
verification-before-completion提交前跑验证命令并确认输出，再声称完成测试/验收
requesting / receiving-code-review主动找人 / 被找审查，按严重度分级、技术严谨不表演式附和协作
writing-plans把已批准的设计拆成「明确到每条命令/校验」的任务清单流程
subagent-driven-development按 plan 为每个 task 派发全新 subagent，两段式 review（先规格后质量）执行
executing-plans按 plan 的另一种执行模式（带人类 checkpoint 分批执行）执行
dispatching-parallel-agents2+ 无共享状态独立任务时的并行派发执行 / 编排

它们并不是互不相干的散装文件——在流程编排上有明确先后依赖。README 的「Basic Workflow」就把主要几条串成了这样一条流水线：

brainstorming→ 批准→ using-git-worktrees→ writing-plans→ subagent-driven-dev / executing-plans→ TDD→ requesting-code-review→ finishing-a-branch

多 harness：一次写了，十几种 Agent 都能用

Superpowers 刻意做成「跨宿主」的思路很突出。README 的安装段覆盖了 Claude Code、Codex（App/CLI）、Cursor、Devin CLI、Gemini CLI、GitHub Copilot CLI、Grok Build CLI、Kimi Code、OpenCode、Pi、Antigravity、Hermes Agent、Factory Droid 等十多种入口。支撑这一跨宿主能力的是两层机制：

  • 每个宿主各有一份插件清单（.claude-plugin、.codex-plugin、.cursor-plugin……），让宿主把它识别成一个可安装的插件；
  • hooks/ 提供了平台无关的 session-start，细节在第三部分展开。
还需注意：Superpowers 官方尚未提供 deepseek-harness（DSH）对应的插件入口，官方安装清单里也没有它。DSH 本地使用通常得走社区/第三方把官方 skills 适配成 DSH 可加载插件的方案——适配时把 skills/ 里各 skill 包装成能被 DSH 的 skill 工具直接调用的形式，并配一份 DSH 专属的 harness 说明。

你会怎么用它

对 Claude Code 用户，最常见的是从官方市场直接装：

/plugin install superpowers@claude-plugins-official

Cursor、Codex、Copilot CLI 各自有自己的安装与搜索命令，安装方式都和宿主绑定。

02第二部分：为什么它受欢迎？它的优点是什么

要理解 Superpowers 为什么火，光看功能清单不够——得先看它解决的是哪个真问题。

它解决的根本痛点：LLM 写码不受纪律约束

直接让一个大型语言模型去「写个待办应用」或「把那个 bug 修掉」，它往往会得到一句模糊指令后马上开始逐行敲代码：先写产品代码、后来才补补测试、遇到失败就乱猜原因、差不多绿了就当完成。这正是现在所有编码 Agent 用户共同的挫败来源——能力强但不可靠。

Superpowers 的立场可以浓缩成一句很硬的话：把「硅谷团队的软件工程纪律」（先厘清需求再做设计、真红绿 TDD、逐个任务验证、主动代码评审、反对过度复杂与重复）不是用「建议」灌输，而是用「不可违背的行为门槛」编码进去。

它在仓库自己的文档里就是这么自述的（README「How it works」一段，描述设计定稿后写出的实施计划）：

…your agent puts together an implementation plan that's clear enough for an enthusiastic junior engineer with poor taste, no judgement, no project context, and an aversion to testing to follow. It emphasizes true red/green TDD, YAGNI (You Aren't Gonna Need It), and DRY.

它甚至假设看这份实施计划的对象是「狂热但没品味、没判断力、没项目上下文、还讨厌测试的新手工程师」——所有步骤都被写到了傻瓜能执行的程度。

README 的 Philosophy 小节则把价值观列成四句：TDD 先行、过程优于瞎猜、化繁为简、证据高于口头声明（Evidence over claims — Verify before declaring success）。

把「流程」从口头提醒改成 agent 必须遵守的强制步骤——这是 Superpowers 最核心的差异化。

优点拆解

  1. 自动触发，几乎零学习成本。「凡是你说『这只是个简单问题』的场景，其实都是一次任务」——这些反合理化内容被写进启动注入里，让新用户不必背任何触发词，属于「开箱就让 agent 行为改变」。
  2. 把方法论做成「插件/版本化」，而非写死的 prompt。skill 可被独立迭代、回滚、评测，还带配套 eval 仓库（superpowers-evals 用真实 tmux 会话判定合规）。prompt 是死文字，skill 是可维护、可验证的「程序」。
  3. 可组合的流水线，而非大而全的单文件。不塞一段 5000 行的超长 prompt，而是拆成 14 个接口清晰、职责单一的 skill，彼此用流程编排衔接。
  4. 面向 agent 行为的「反合理化」设计。针对「这小事不用走流程吧」的念头逐条写进 Red Flags 表——是写给「不情愿的 LLM」读的流程文档，不是写给人读的。
  5. 零第三方依赖 + 跨 harness。「zero-dependency plugin by design」，换 IDE 不失方法论；对十几种 harness 做了适配。
  6. 围绕真实使用中的 bug 持续打磨。release notes 会记录来自真实的坑（如修复 bash 5.3 下 heredoc 挂起）。

略带批判：没有灵丹妙药的部分

作为独立分析，不该只报喜——

  • 全流程仪式感并不对每种任务都划算。brainstorming 连「改一行 flag」也会要求两句短设计 + 点头 gate，对速改型开发者可能显得重。
  • 它依赖「它的方法论假设是对的」。若你认为原型、临时脚本、自由探索本就不该有这么多 gate，这套偏「重编码实践」的方法论未必处处最优。
  • 「自动触发」依赖宿主真的承接会话启动注入。没有就只是「躺在磁盘、不会被自动想起的 md」——所以官方 Integration 验收极严：新宿主必须在全新会话里敲一句 Let's make a react todo list 就自动触发 brainstorming，否则不算有效集成。
  • 外部可独立复核的证据偏少。第三方基准、横向评价的可信对比例证不多，星数这类外部数值建议以官方 page 为准。

03第三部分：从源码看它的实现

这一部分瞄准两个问题：md 是怎么写的、script 是怎么写的，再连起来讲清「skill 如何被自动触发」这条运行链路。

3.1 · .md 怎么写：解剖一份 SKILL.md

每个 skill 的主文件统一叫 SKILL.md，顶层由一个 YAML frontmatter + 自由格式 Markdown 正文组成。frontmatter 是 harness 用来把它注册进「Skill 工具/索引」的元数据；正文才是决定 agent 行为的内容。以元技能 using-superpowers/SKILL.md 为例：

---
name: using-superpowers
description: Use when starting any conversation - establishes how to
  find and use skills, requiring skill invocation before ANY response
  including clarifying questions
---

name 是带连字符的唯一 ID；description 是最关键的触发信号——它要写成「在什么场景下『应该』被触发」的高信号引导句，harness 靠比对当前任务与该 description 决定要不要载入这份文档。作者甚至会把 You MUST use this before any creative work 这类「强制词」嵌进去以提升命中。

内核组织有一套非常统一的「写法六式」——

  1. 门控块把「不许做」提到视觉上无法忽略。 brainstorming 开头有 <HARD-GATE>，using-superpowers 里是 <EXTREMELY-IMPORTANT>。这些 XML/HTML 式标签让模型把「这是规则」与「这是解释」区分开，例如： 
    <EXTREMELY-IMPORTANT>
If you think there is even a 1% chance a skill might apply...
YOU ABSOLUTELY MUST invoke the skill.
</EXTREMELY-IMPORTANT>
  2. 用「Red Flags」表格专门堵 agent 的借口。 文档预设读者「会自己找台阶」，于是把台阶逐条列出。例如 using-superpowers 里的 Rationalizing 检查表（原表节选）：
    ThoughtReality
    「这只是个简单问题」问题都是任务，先查 skill。
    「我需要更多上下文再问」skill 检查要在澄清问题之前。
    「这不需要走正式流程」如果存在 skill，就用它。
    「我先探索下代码库」skill 告诉你怎么探索，先查。
    「我大概知道 skill 讲什么」skill 会演进，请读当前版本。
  3. 正文 = 路径判定 + 逐条可勾选清单。brainstorming 把任务分成 spike / bounded / architectural 三条路径、每条给出编号清单，并把「先把任务分类说出来」写成显式行为。
  4. 用流程图 / 表表达「过程」。仓库里连状态机都用 dot 图嵌在 md 里画成分支，能用图/表/命令表达的就不写啰嗦散文。
  5. 控文件体积、分层引用。SKILL.md 通常 60–700 行，重型参考独立成文件（references/ 放各 harness 平台差异说明，如 codex-tools），正文保持精准命中当前判断、必要时再展开重型参考。
  6. 把方法论讲成可复用模板。writing-skills 甚至说：写 skill 本身就该像 TDD——先用子 agent「压测」观察它会不会违规（RED baseline），再写正文（production），验证合规（GREEN）、再堵漏洞（refactor）。这套反合理化约束是被「评测失败逼出来的」，不是漂亮话。

3.2 · script / hook 怎么写：让 skill 在正确时机自动出现

如果 md 是「大脑里的规则」，hooks/ 与脚本就是「叫醒大脑记得用规则的闹钟」。钥匙在这个目录里：

hooks/
  hooks.json            # Claude Code 使用（SessionStart + matcher 事件）
  hooks-cursor.json     # Cursor 单独（sessionStart 事件格式不同）
  run-hook.cmd          # cmd + bash 双栖跨平台调度器
  session-start         # 无扩展名的真正注入脚本

a) hooks.json：声明「什么事触发什么」

{
  "hooks": {
    "SessionStart": [
      { "matcher": "startup|clear|compact",
        "hooks": [
          { "type": "command",
            "command": "\"${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd\" session-start",
            "shell": "bash", "async": false }
        ] } ] } }

即：宿主在 session startup / clear / compact 时命中该事件，同步执行 run-hook.cmd session-start。async:false 表示它必须被同步执行——因为其副作用是把返回值写进上下文，得等它。

跨宿主难点立刻暴露：hook 配置与事件名随宿主不同——Claude Code 用大写 SessionStart + matcher + 绝对路径；Cursor 用 camelCase sessionStart + 相对命令。所以仓库必须维护多份 json 并让脚本自判平台。

b) run-hook.cmd：一个文件同时是 cmd 与 bash

为了让同一段逻辑既能在 Windows(cmd) 又能在类 Unix(bash) 跑，作者用了「双语外壳」——文件片段对 cmd 是批处理、对 bash 是无害注释块：

: << 'CMDBLOCK'
@echo off
REM Windows 段：找 Git for Windows bash...
if exist "C:\Program Files\Git\bin\bash.exe" (
  "C:\Program Files\Git\bin\bash.exe" "%HOOK_DIR%%~1" %2 %3 %4 %5 %6 %7 %8 %9
  exit /b %ERRORLEVEL%
)
... （找不到 bash 则静默 exit /b 0 优雅降级）
CMDBLOCK

# Unix: run the named script directly
SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
SCRIPT_NAME="$1"; shift
exec bash "${SCRIPT_DIR}/${SCRIPT_NAME}" "$@"

这里有两个值得记的工程权衡：

  • hook 脚本刻意不带 .sh 扩展名——否则 Claude Code 的 Windows 自动探测会把含 .sh 的命令擅自前置 bash，破坏 cmd 路径。
  • 没有 bash 就静默退出 0——降级不报错：插件仍可用，只是少了一次上下文注入。

c) session-start：把整份 using-superpowers 灌进上下文

不带扩展名的 session-start 是整条链路的心脏。剥掉注释后，骨架（示意性精简）长这样：

#!/usr/bin/env bash
set -euo pipefail
PLUGIN_ROOT="$(cd "$(dirname "$0")/.." && pwd)"

# 读整份 using-superpowers 内容
content=$(cat "$PLUGIN_ROOT/skills/using-superpowers/SKILL.md")

# 用 bash 参数替换做 JSON 转义（单遍，比逐字符 for 快几个数量级）
escape_for_json() {
    local s="$1"
    s="${s//\\/\\\\}"; s="${s//\"/\\\"}"
    s="${s//$'\n'/\\n}"; s="${s//$'\t'/\\t}"
    printf '%s' "$s"
}
escaped="$(escape_for_json "$content")"
session_context="<EXTREMELY-IMPORTANT>
You have superpowers.
**Below is the full content of your 'superpowers:using-superpowers' skill…**
${escaped}
</EXTREMELY-IMPORTANT>"

这段代码里的真实功夫，件件都有据可查的注释：

  • 注入的对象就是「技能本身」：把整份 using-superpowers/SKILL.md 包进 <EXTREMELY-IMPORTANT> 当作会话的额外上下文——模型一进场就先看到「你拥有 superpowers，下面是教你怎么用技能的技能」。
  • 转义用 bash 参数替换 `${s//old/new}`——注释直白写道这是「C 级单遍，几百倍快于字符循环」，是在 session start 里抠毫秒的严谨编码。
  • 按平台输出不同 JSON 结构：Cursor 设了 CURSOR_PLUGIN_ROOT → 顶层 additional_context；Claude Code 设了 CLAUDE_PLUGIN_ROOT → hookSpecificOutput.additionalContext（嵌套）；其余（Copilot CLI 等 SDK 标准）→ 顶层 additionalContext。注释提醒「Claude Code 两个字段都读且不去重，所以只发当前平台那一个」。
  • 用 printf 而非 heredoc——明确点出是为了绕开 bash 5.3+ 读取 heredoc 的挂起 bug（issue #571），连边角 bug 都留了可检索的 issue 号。

回答「script 怎么写」：能不用脚本就不用；真到要处理跨平台/跨宿主时，用 polyglot、显式平台分支，并给每个坑写可读注释。

3.3 · 运行链路：为什么你什么都不用做，它会自己启动

把 md 与 hook 拼起来，一条完整链路出现了：

  1. 你在宿主里装好并新开会话（或 /clear、/compact）。
  2. 宿主在 SessionStart 命中 hooks.json 里 matcher: startup|clear|compact。
  3. 宿主同步执行 run-hook.cmd session-start → 找到 bash → 跑 session-start。
  4. 它读 using-superpowers/SKILL.md，包进 <EXTREMELY-IMPORTANT>、按平台挑好 schema，作为 additionalContext 返回。
  5. 宿主把这内容当作「会话第一批上下文」注入——模型在见到你打的任何字之前，就先看到「拥有 superpowers + 有 1% 可能适用就绝对要调 skill」。
  6. 于是当你打出「我们做个 react 待办吧」时，模型带着启动指令先想「brainstorming 适用」→ 真的去 Skill 载入 brainstorming/SKILL.md——「自动触发」就发生了。
会话启动→ SessionStart hook→ 注入 using-superpowers→ agent 先查 skill→ 自动调 brainstorming…

仓库把这条验收做成客观判据：在任意新 harness 里开全新会话、只敲一句

Let's make a react todo list

能自动触发 brainstorming（不需要用户手动指定）才叫「真集成」；「只手动拷文件 / 用 npx skills 运行时 shim / 让用户每会话手动 opt-in」都被判不成立。因为它看透了关键事实——没有 session-start 这条「自举闹钟」，所有 skill 都只是一堆躺在磁盘上、不会被自动想起的 md。

04第四部分：总结与启示

Superpowers 并没有发明「该做 TDD、该先想清楚需求」这些原则——它把原则从「写给工程师看的手册」翻译成「写给会狡辩的编码 agent 看、会在正确时机自动出现、历经评测打磨的代码」。它受欢迎的本质，是敏锐地识别并解决了一个真实体验问题：

LLM 有能力+自动注入的纪律=可靠

对你（无论用它还是写同类 skill）的四点收获：

  1. 描述决定触发，正文决定行为。想让 skill 真的被用，先把 frontmatter 的 description 写成能高信号命中的触发句，再用 checklist + 门控块钉住硬约束。
  2. 自动触发胜过手动使用。一个要你手动敲开关的 skill 是「死技能」；真正强的是像 session-start 那样在事件里把「如何正确思考」当上下文喂进去。
  3. 像写测试那样打磨文档。RED→GREEN→REFACTOR 不只对代码成立——行为类文案靠「压测子 agent + 合规检查」的 eval loop 迭代，而不是一拍脑袋写漂亮话。
  4. 想跑「业务能力」就往插件层走，别只停在 skill。skill 是「行为方法论」，一个完整能力往往还需注入工具、hooks、开机引导——把若干 skill 连同会话级装配打包成宿主认识的「插件」，层级比单个 skill 更高、更能承载业务闭环。但插件语义依赖 harness 是否支持（清单能否被识别、会话能否被承接）——像我们所处的内部平台 co-claw 就尚未开放插件安装，现阶段只能依赖 skill 层先行。

它至今仍是社区里「低门槛、开源、零依赖 + 已打磨 skill + 会话级自动激活」三者结合的典型案例。想给你的 agent 加方法论？把它当成一套值得解剖的成品蓝本——也要记得它自身划的底线：它不是银弹，只在宿主正确承接 bootstrap 时才成立，也只对你的编码风格「恰好需要这种强 gate」时最合适。
